# Серверное избранное — 18 октября 2026

Frontend подключён к текущим Favorite model/serializer/views/urls. Backend, миграции, БД, .env, Login/Register и JWT-прокси не изменены. Уточнение поведения: локальное избранное удалено полностью; API — источник данных по умолчанию, Demo только явный просмотр без сохранения избранного.

## Проверенный контракт

| API относительно /api/v1/catalog/ | Использование |
| --- | --- |
| GET favorites/ | Избранное текущего пользователя; массив либо стандартная DRF-пагинация |
| POST favorites/ | Только `{ "product": productId }`; 201 при создании, 200 при повторном добавлении |
| DELETE favorites/{favoriteId}/ | Удаление записи избранного, НЕ productId; успешный 204 |

Ответ FavoriteSerializer: `{ id, product, created_at }`. `user` — HiddenField и не отправляется frontend. Вложенных данных товара нет: карточки соединяются с существующим публичным каталогом по product PK. Если товара в каталоге уже нет, запись остаётся видимой как недоступная и её можно удалить по favorite ID.

Список ограничивается user на backend; object permissions защищают удаление. Frontend не заменяет эти проверки. Динамический существующий `/api/backend/v1/...` proxy сохраняет прежние HTTP-only JWT cookies и refresh-flow; новых backend URLs нет.

## Что работает в UI

- Общая FavoritesProvider для сердец в коллекции/PDP/связанных товарах, счётчика шапки и страницы `/favorites`.
- Гостю предлагается вход в обоих режимах. Сессия всегда читается через `/auth/me`, без исключения для Demo. Старые `api:*` и `demo:*` ключи браузера не используются и не импортируются; имеющиеся browser-данные не удалялись.
- Даже аутентифицированный пользователь не может сохранить demo-товар: отдельное состояние Demo объясняет, что необходим рабочий каталог. Совпадающие числовые ID не отправляются в чужое пространство данных.
- Список кешируется отдельно для user ID и удаляется после ухода последнего потребителя. При смене аккаунта чужие записи не отображаются. Возврат фокуса обновляет серверную выборку.
- На время добавления/удаления все экземпляры кнопки одного товара заблокированы общим lock. Повторный клик не создаёт второй запрос. Разные товары можно изменять независимо.
- UI обновляется после подтверждённого ответа, не оптимистически. Ошибка POST/DELETE показывается уведомлением, не заменяется локальным успехом; автоматических повторов записи нет. DELETE 404 считается уже выполненным удалением, после чего перечитывается список.
- Есть loading/skeleton, пустая подборка, запрос входа, ошибка с retry, сохранённый недоступный товар. 401 списка не показывается как пустое избранное. При ошибке чтения сердца временно заблокированы; повтор доступен со страницы избранного.
- Существующая адаптивность, оба цветовых режима и доступные названия сердец сохранены. Pending обозначен disabled/aria-busy, выбранность — aria-pressed.

## API и Demo

Источник соответствует существующему `SIFAT_CATALOG_SOURCE` — не новая независимая настройка, способная перепутать одинаковые product ID. `data-source.ts` задаёт единый выбор для витрины и админки. Без переменных обе работают с API; backend-ошибки не запускают Demo. Админка в API-режиме меняет реальные данные после явных действий пользователя и проверки прав.

```sh
# Из frontend/, без изменения .env
SIFAT_CATALOG_SOURCE=api SIFAT_ADMIN_SOURCE=api npm run dev
```

В production те же переменные задаются при `npm run start` после build. `DJANGO_API_ORIGIN` остаётся прежней настройкой адреса Django.

Явный просмотр Demo: `SIFAT_CATALOG_SOURCE=demo npm run dev`. В нём избранное НЕ сохраняется ни локально, ни в Django. Императивный local-only toggle удалён. Даже Demo не обходит вход и не заявляет фиктивный успех. Серверные favorites доступны только для API-товаров. Заказы/корзина не подключались и не создавались. При отсутствии Django рабочая витрина покажет ошибку API, а не демотовары; backend необходимо запускать отдельно.
