# Sifat Mebel: разделение витрины и управления

Актуальное дополнение 12 октября: [единая карточка и создание товара через UI](PRODUCT-WORKFLOW.md). Добавлены `/admin/products/new`, `/admin/products/[id]` и вход из шапки/мобильного меню. Финальная проверка этого дополнения: ESLint, TypeScript, production build, 53/53 Playwright.

Обновление 11 октября 2026. Изменения агента — только `frontend/`. Backend, БД, миграции, .env и Login/Register не редактировались. Backend-файлы менялись владельцем во время работы; это учтено при повторной read-only сверке.

## Покупательские маршруты

- `/` — главная.
- `/catalog`, `/categories`, `/categories/[slug]`, `/search` — каталог, категории, типы, поиск/фильтры.
- `/products/[slug]` — товар, галерея, структурированные варианты, цена/наличие, избранное, контакт.
- `/favorites` — локальное избранное.
- `/account` (алиас `/profile`), `/addresses` — существующие профиль/адреса.
- `/contact` — связь с магазином.
- `/auth/*` — существующая авторизация, восстановление, email verification.

На витрине нет создания/редактирования каталога, настройки характеристик и склада. В профиле подтверждённого администратора появляется только **ссылка** «Управление магазином». Кнопки управления находятся внутри `/admin`, не рядом с товарами витрины. Существующие legacy cart/checkout/order URL по-прежнему ведут к контактам.

## Административные маршруты и API

Пути API ниже относительно `/api/v1/catalog/`. Реальный адаптер отправляет запросы через существующий cookie/JWT frontend-прокси; токены недоступны клиентскому JS.

| Маршрут frontend | Функция | Существующий Django API |
| --- | --- | --- |
| `/admin` | Обзор, счётчики, порядок наполнения | Списки товаров/вариантов/категорий/движений |
| `/admin/categories` | CRUD категорий, обложка, SEO | `categories/`, `categories/{id}/` |
| `/admin/product-types` | CRUD типов и связи с категорией | `product-types/`, `product-types/{id}/` |
| `/admin/brands` | CRUD брендов, логотип | `brands/`, `brands/{id}/` |
| `/admin/products` | Создание/редактирование/архивация товара | `products/`, **`product/{id}/`** |
| `/admin/product-images` | Фото, подпись, основное фото, порядок | **`product-image` без завершающего слеша**, `product-image/{id}/` |
| `/admin/attributes` | Определения TEXT/NUMBER/BOOLEAN | `attributes/`, `attributes/{id}/` |
| `/admin/product-type-attributes` | Схемы типов, опции, фильтры | `product-type-attributes/`, `product-type-attributes/{id}/` |
| `/admin/product-attribute-values` | Типизированные значения товара | `product-attribute-values/`, `product-attribute-values/{id}/` |
| `/admin/product-variants` | SKU, цены/скидки, активность | `product-variants/`, `product-variants/{id}/` |
| `/admin/variant-attribute-values` | Структурированные значения SKU | `variant-attribute-values/`, `variant-attribute-values/{id}/` |
| `/admin/stock-adjustments` | Подтверждаемые приход/списание | POST `stock/adjust/` |
| `/admin/stock-movements` | Неизменяемый журнал | GET `stock/movements/` |

CRUD: GET списка, POST создания, PATCH изменения, DELETE удаления. DELETE товара соответствует `archive()` backend, поэтому обозначен «В архив». История склада не имеет кнопок изменения/удаления. Остаток не редактируется напрямую в варианте: новый SKU получает backend-default 0, изменения проводятся через stock API.

Payload склада: `{ variant_id, operation: "IN" | "OUT", quantity, reason }`. Идемпотентность backend не заявлена: двойной клик блокируется, автоматического retry нет; при неопределённом сетевом результате интерфейс предлагает сначала проверить журнал. Поиск по таблицам и фильтр журнала выполняются локально по загруженным страницам, без выдуманных query-параметров Django.

## Проверка доступа — не только скрытие кнопок

1. `AdminShell` проверяет `GET /auth/me` через действующий JWT/cookie-прокси. Локально сохранённая роль и декодированный JWT не используются.
2. Доступ разрешён только роли `ADMIN` из реального `/auth/me`. `USER` — покупатель. Неиспользуемая `MANAGER`, неизвестные роли и даже `USER` с разрешающим ответом permission probe не получают вход в управление.
3. Выполняется **OPTIONS `/catalog/stock/movements`**. Текущий Django view защищён `IsAdminOnly` (ADMIN либо staff), включая OPTIONS. Ответ подтверждает разрешение backend, но **не доказывает `is_staff`**: этого поля нет в MeSerializer.
4. Только после успеха монтируются административные страницы и выполняются их запросы. При 401 — вход, при 403 — отказ, при неизвестной роли/ошибке проверки — закрытое состояние с повторной попыткой. Демо не обходит проверку.
5. Повторная проверка при смене admin-маршрута, восстановлении фокуса и каждые 60 секунд. **Перед каждой записью** проверяются сессия, тот же пользователь и разрешение; 401/403 закрывают управление.
6. Даже если изменить frontend через DevTools, реальные разрешения остаются на стороне Django. Клиентский guard не заявлен заменой backend-permissions. Приватные API-данные не включаются в SSR до проверки клиента.

Frontend намеренно допускает только рабочую роль ADMIN, даже если backend предоставляет staff дополнительные права. Сервер остаётся окончательной границей разрешений каждой операции. ADMIN без staff может управлять основным каталогом и читать журнал, но создание категории и корректировка остатка сейчас возвращают 403: эти два backend view всё ещё используют IsAdminUser. Ошибка показывается честно, без подмены API на mock.

## Real API и mock

Каждая функция из таблицы имеет **реальный адаптер существующего endpoint** и изолированную демореализацию. В текущей конфигурации без переменных используется demo, как и витрина. Режим всегда подписан вверху админки.

Выбор источника: `SIFAT_ADMIN_SOURCE`, иначе `SIFAT_CATALOG_SOURCE`, иначе `demo`. Переменная `api` включает API; ошибка API никогда не превращается в «успешное» mock-сохранение.

Запуск из `frontend/`, без редактирования .env:

```sh
# Учебное управление; сессия, роль ADMIN и доступ всё равно проверяются в Django
SIFAT_ADMIN_SOURCE=demo npm run dev

# Реальное управление и реальная витрина
SIFAT_ADMIN_SOURCE=api SIFAT_CATALOG_SOURCE=api npm run dev

# Production: источник выбирается при старте сервера
npm run build
SIFAT_ADMIN_SOURCE=api SIFAT_CATALOG_SOURCE=api npm run start
```

Демо использует существующие response-shaped fixtures `commerce/mock/catalog.ts`. Изменения сохраняются в `sessionStorage` отдельно для пользователя, живут в текущей вкладке и не публикуются ни в Django, ни в покупательский mock-каталог. Для демо реализованы CRUD, уникальность slug/SKU и связей атрибутов, защита связанных записей, проверка остатка, журнал. Недостаток места в storage показывается ошибкой, а не фиктивным успехом.

Во всех режимах реальными остаются `/auth/me` и проверка доступа. Демо — изолированное учебное управление, не утверждение о наличии staff у пользователя. Реальных backend-записей агент не выполнял. Работа адаптеров и прокси проверена тестовыми ответами/изолированным HTTP stub, а не созданием данных магазина.

## Адаптивность и доступность

Отдельные header/sidebar/main, без витринных footer/bottom navigation. Общие цвета и шрифты сохранены; minimalist-ui использован для спокойной рабочей композиции, без SaaS-градиентов и больших скруглений.

- Ниже 1024 px меню переходит в drawer, контент занимает всю ширину.
- Ниже 768 px строки таблиц становятся вертикальными карточками с подписями полей; формы имеют шрифт 16 px и touch targets от 44 px.
- На 320–429 px компактнее поля/отступы, одноколоночные рабочие блоки.
- Desktop: боковое меню, таблицы, ограниченная ширина; 1920 px без бесконечно растянутых форм.
- Нативные label/fieldset, aria-invalid и связанный текст ошибок, фокус на первой ошибке, aria-current, live-статусы, dialog trap/Escape/возврат фокуса. Во время записи поля и повторное подтверждение заблокированы.

## Ограничения backend, обнаруженные только чтением

- Все требуемые CRUD и stock endpoints уже присутствуют: новые маршруты backend для этой админки не создавались.
- GET категорий возвращает только активные записи даже сотруднику. Для полноценного управления выключенными категориями нужен staff-aware список/контракт. В API-режиме интерфейс предупреждает об этом.
- `MeSerializer` не содержит staff/capabilities. OPTIONS журнала проверяет доступ к управлению, а не наличие staff. Для точного предварительного отключения отдельных операций предпочтителен явный capability-контракт.
- Во время работы владелец исправил `ProductSerializer.brand` и возврат `attrs` в `validate`; устаревшее предупреждение удалено из UI.
- Повторное чтение 11 октября: общий permission использует корректное сравнение `user.role == UserRole.ADMIN`; прежнее предупреждение о `.role.ADMIN` больше не актуально. Создание категории и корректировка склада всё ещё требуют staff. Backend не редактировался.
