# Покрытие API и работа с атрибутами

Аудит: 18 октября 2026. Не все возможности backend имеют полноценный frontend. Ниже — фактическое покрытие, а не обещание поддержки каждого endpoint/HTTP-метода.

## Как добавить атрибут и значение

Войдите как **ADMIN** → `/admin/products` → откройте товар → **Характеристики** → **Добавить атрибут и значение**.

1. Выберите существующий атрибут или создайте новый: название, slug, тип TEXT / NUMBER / BOOLEAN, единица измерения.
2. Если привязки ещё нет, сохраните её для ProductType товара. Здесь задаются обязательность, фильтрация и порядок. Схема общая для всех товаров этого типа.
3. Введите и сохраните значение. Поле зависит от типа атрибута; `0` и `false` не теряются. Существующее значение изменяется PATCH-запросом, а не создаётся повторно.

Для характеристики конкретного варианта откройте **Опции вариантов**, выберите активный вариант и используйте ту же кнопку. Если существующая привязка не разрешает опции вариантов, мастер предлагает обновить её (`can_be_variant_option=true`), не создавая дубликат.

Это последовательные запросы к существующим API, **не транзакция**. Если определение создано, а привязка не сохранилась, определение остаётся на сервере. Можно повторить сохранение привязки или позже выбрать это определение. Ошибки Django выводятся в форме; успешное сохранение не имитируется.

Backend требует привязку Attribute к ProductType до записи значения. Для варианта дополнительно требуется `can_be_variant_option`. До этого обновления отдельные CRUD-формы уже были, но этот порядок действий не был достаточно понятен. Это обнаруженный UX-пробел, не доказательство причины конкретной ошибки на вашем работающем сервере.

## Что подключено

| API / функция | Интерфейс и состояние |
| --- | --- |
| Categories, ProductTypes, Brands | Отдельные CRUD-страницы `/admin/categories`, `/admin/product-types`, `/admin/brands` |
| Products | Список, создание `/admin/products/new`, редактирование `/admin/products/[id]`; витрина читает каталог |
| Product Images | Загрузка и управление фотографиями в карточке товара и `/admin/product-images` |
| Attributes | CRUD `/admin/attributes`, создание из карточки товара |
| ProductTypeAttributes | CRUD `/admin/product-type-attributes`, привязка в новом мастере |
| ProductAttributeValues | CRUD `/admin/product-attribute-values`, типизированное значение в карточке товара |
| ProductVariants | CRUD `/admin/product-variants` и вкладка карточки товара |
| VariantAttributeValues | CRUD `/admin/variant-attribute-values`, мастер с выбором варианта |
| Stock | Корректировка `/admin/stock-adjustments`, история `/admin/stock-movements`; окончательное разрешение проверяет backend |
| Favorites | Серверные GET/POST/DELETE, карточки и `/favorites`; гостю нужен вход, локального обхода нет |
| Auth | Регистрация, вход, refresh, выход, подтверждение/resend email, forgot/reset password, me |
| Profile | Чтение и изменение основных полей профиля |
| Addresses | Список, создание, изменение, удаление |

В API-режиме управление отправляет реальные запросы через существующий адаптер и JWT-прокси. Перед изменениями повторно проверяется сессия ADMIN; серверные permissions остаются границей безопасности. USER и неиспользуемая роль MANAGER не получают интерфейс управления.

## Что ещё не завершено

- Смена пароля авторизованным пользователем (`auth/change/password/`): нет отдельной формы.
- Выход со всех устройств: метод адаптера есть, кнопки в интерфейсе нет.
- Аватар профиля: отображение есть, загрузки через UI нет.
- Координаты адреса: нет отдельного редактора.
- Поиск/цена/бренд/категория/сортировка каталога подключены к серверу вместе с пагинацией. Фильтры по ProductType/характеристикам/остаткам backend пока не поддерживает, в API-режиме они не имитируются.
- Витрина товара теперь использует отдельный detail GET по ID. Для управления есть ограничение неполных management-полей в detail; решение и пределы описаны в [PAGINATION.md](PAGINATION.md).
- Корзина, checkout и заказы не реализованы как реальная покупка: старые маршруты ведут к контакту магазина. Новые backend API для них не создавались.

Для добавления атрибутов и значений необходимые API уже существуют; новый backend endpoint не требуется. Если работающий Django отклонит запрос, нужна конкретная ошибка ответа — её мастер показывает, а не заменяет demo-успехом.

## Данные и проверки

API — источник по умолчанию. Изолированный Demo доступен только при явном выборе источника и не служит запасным ответом на ошибку Django. Избранное в Demo не сохраняется. Новый мастер использует те же адаптеры, что существующие формы.

Новые браузерные тесты `tests/admin-attributes-api.spec.ts` запускают отдельный HTTP-стенд с контрактом проверенных сериализаторов. Они проверяют порядок запросов, typed payload, null для остальных колонок, NUMBER=0, BOOLEAN=false, PATCH существующего значения/привязки, повтор после ошибки и drawer 320 px. Это интеграционные проверки frontend, **не POST в вашу Django-БД** и не замена живой проверки сервера.

Изменённые frontend-файлы: `attribute-setup.tsx` (новый), `product-workspace.tsx`, `resource-form.tsx`, `resource-manager.tsx`, `lib/admin/resources.ts`, `lib/admin/forms.ts`, новый API-тест, этот отчёт и README. Backend, .env, миграции, Login/Register и auth-layout не редактировались.

Проверки: ESLint — успешно; TypeScript — успешно; production build — успешно; Playwright — **69/69**. Существующая матрица адаптивности: admin 320/375/390/430/768/1024/1280/1440/1920 px; витрина дополнительно 2560 px. Новый сценарий атрибутов отдельно проверен на 320 px, включая отсутствие горизонтального переполнения drawer; снимок просмотрен вручную.

Дизайн сохранён с использованием `minimalist-ui`: существующие формы, drawer и стили вместо нового визуального языка. Поля имеют связанные label, неизменяемые FK заблокированы, состояния сохранения и ошибок доступны, drawer использует существующие focus trap, Escape и возврат фокуса.
