## Повторный аудит 21 октября 2026

На момент проверки `while (url)` уже отсутствовал: ранее внедрённая загрузка одной страницы сохранена и повторно проверена. В этом этапе исправлена оставшаяся регрессия: detail мог показывать положительный остаток варианта у товара OUT_OF_STOCK. Теперь существующий серверный `status` сохраняется в view model, общий mapper оставляет товар видимым с `available=false` и `stock=0`, а detail не перекрывает это состояние выбранным вариантом. ### Что требуется от backend для следующих улучшений

Это **предложения**, не существующие API-контракты и не реализованные frontend-запросы:

1. Точный фильтр ProductType по ID. Существующий SearchFilter по имени типа не заменяет такой фильтр.
2. Типизированные фильтры атрибутов (TEXT/NUMBER/BOOLEAN), валидация принадлежности ProductType и `is_filterable`; значения `0` и `false` должны сохранять смысл. Диапазоны чисел и формат параметров необходимо согласовать с backend.
3. Для опций вариантов — совместное выполнение всех ограничений на **одном активном SKU**, а не на разных вариантах одного товара. Фильтрация — до пагинации, без дублирования Product в count/results.
4. Глобальные фасеты: доступные значения и счётчики по отфильтрованному набору магазина **до пагинации**, не только по текущим 20 товарам. Сейчас такие данные frontend не выдумывает.
5. Фильтр наличия и публичная сводка stock с согласованным приоритетом статуса товара. Складские корректировки не должны заменяться frontend-вычислениями. Цена текущих фильтров — именно Product.base_price; фильтрация по цене варианта/скидке требует отдельного бизнес-решения.
6. Preview основного изображения в списке продуктов либо фильтр images по выбранным товарам. Сейчас сохраняется один общий кешируемый GET images: число запросов ограничено, но объём этого справочника всё ещё зависит от размера каталога.
7. Стабильный tie-breaker порядка страниц, например PK при одинаковых created_at/base_price. Сейчас backend разрешает ordering только по base_price/created_at; frontend не отправляет неразрешённое ordering=id и не пытается досортировать отдельно текущую страницу.

Проверки используют исходный код реальных Django фильтров/serializer и изолированный HTTP-стенд с их форматом ответов. Это не live-запись в вашу БД, не прогон Django-тестов и не нагрузочный benchmark production.

## Что исправлено

Frontend больше не обходит `next`, чтобы объединить весь каталог. Пагинация используется **только для products**, как в текущем Django. Categories, ProductTypes, Brands и Product Images остаются обычными массивами. Название основного раздела в навигации и заголовке изменено на «Каталог»; маркетинговое слово «коллекция» не означает отдельный backend-ресурс.

| Экран | Загрузка товаров |
| --- | --- |
| Каталог, поиск, категория | Один GET `products/?page=N&page_size=20`; `count` берётся с сервера |
| Главная | Один GET `products/?page=1&page_size=4` |
| Список категорий | Ни одного GET products, только навигационные справочники |
| Карточка товара | Один GET `product/{id}/` с вложенными изображениями, характеристиками и вариантами |
| Избранное | Детали только 20 сохранённых товаров текущей страницы, максимум 4 одновременно; публичный detail cache клиента — 30 секунд |
| Управление → Товары | Одна страница по 20 записей, серверный поиск по подтверждению, серверный count |
| Выбор товара в связанных формах | Отдельный постраничный поиск, без скачивания всех товаров в select |

На холодной загрузке каталога дополнительно нужны categories, brands и product-image: до **четырёх JSON-запросов catalog API**, не четыре на каждую карточку. Главная пропускает brands — до **трёх** таких запросов. Авторизация, избранное и загрузка самих файлов фотографий считаются отдельно; это не обещание четырёх HTTP-запросов на всю страницу. Список категорий отдельно загружает categories/product-types, без products. Общие справочники/изображения кешируются Next на 60 секунд. Products и detail читаются без серверного кеша; одинаковый detail для metadata и страницы дедуплицируется в рамках React-render. Для product-card и ссылок пагинации отключён автоматический prefetch. Пустой результат products не запрашивает images.

## Фильтры и URL

- UI `q` → API `search`, `category` → `category_id`, `brand` → `brand_id`, `min/max` → `min_price/max_price`.
- Сортировка: `base_price`, `-base_price`, `-created_at`, `created_at`. UI явно называет диапазон **базовой ценой**, не ценой варианта со скидкой.
- Поиск отправляется после submit; цена — после «Применить цену». Набор цифр в полях не отправляет запрос на каждый символ.
- Изменение фильтра/сортировки сбрасывает страницу на первую. URL сохраняет фильтры и `page`; работают reload и browser Back/Forward.
- Переходы «Назад/Далее» строятся из локального URL. Backend `next` не используется ни как адрес запроса, ни как ссылка навигации.
- Неверный формат page нормализуется в 1; отсутствующая страница, которую Django отклоняет 404, открывает существующий экран 404. Ошибки API не заменяются Demo.

Backend пока не поддерживает точную фильтрацию по ProductType, динамическим значениям и остаткам, а также сортировку по названию. В API-режиме эти элементы не имитируются фильтрацией текущих 20 товаров: скрыты, ограничение описано в панели фильтров. В явном Demo прежние локальные фильтры сохранены.

## Карточка и избранное

API-ссылки товара теперь `/products/{id}`, потому что существующий Django detail принимает PK, не slug. Demo сохраняет slug-ссылки. Старые API slug-only закладки показывают объяснение и переход в каталог, **не запускают скрытое сканирование всех страниц**. Для сохранения прежних slug-ссылок без сканирования backend потребуется lookup по slug; здесь он не выдумывался.

List serializer не содержит вариантов/остатков. На карточке списка выводится базовая цена; точное наличие не выдумывается. Статус OUT_OF_STOCK отображается как отсутствие, сам товар не пропадает. Detail получает реальные вложенные данные и сохраняет значения `false`/`0`. Дополнительный список рекомендаций не запрашивается ради открытия detail.

Favorites API отдаёт ID товаров, поэтому нужны отдельные detail-запросы. Они идут только для видимой страницы, с ограничением параллельности и кешем. Только 404 означает недоступный товар; 5xx отображается как ошибка с повтором. Гости не загружают детали избранного, локального обхода авторизации нет. `/api/store/products/{id}` — frontend read-only маршрут к **существующему** публичному Django detail, без передачи staff JWT.

## Управление и ограничения backend

Список товаров и FK-поиск используют страницы по 20. При открытии товара из списка полная строка переиспользуется из user-scoped query cache, без повторной загрузки каталога. Общие данные управления кешируются на 30 секунд и инвалидируются после записи; ручное обновление также инвалидирует их. Проверка роли перед каждой записью сохранена.

При прямом открытии `/admin/products/{id}` без кеша возникает ограничение существующего `ProductDetailSerializer`: в GET нет `is_active`, `is_featured`, простых FK и некоторых полей управления. Чтобы не подставлять ложные defaults, адаптер читает detail и **одну** страницу списка с поиском по имени (`page_size=100`, максимум backend). Если искомый ID не попал в эти 100 совпадений, форма показывает ошибку и предлагает открыть товар из списка. Для полного устранения этого редкого ограничения backend нужны полные management-поля detail либо фильтр по ID. Django не изменялся.

Endpoint изображений не имеет фильтра по товарам/пагинации и list serializer не включает главное изображение. Поэтому сохранён один общий кешируемый GET изображений. Для ограничения именно объёма этих данных backend позднее нужен preview в ProductSerializer или фильтр images; frontend не отправляет выдуманные параметры.
