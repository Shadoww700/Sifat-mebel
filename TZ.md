# ТЕХНИЧЕСКОЕ ЗАДАНИЕ

## Веб-приложение интернет-магазина «Sifat-Mebel»

---

# 1. Общая информация

## 1.1. Название проекта

**Sifat-Mebel**

## 1.2. Тип проекта

Современное полнофункциональное веб-приложение интернет-магазина.

Магазин изначально специализируется на мебели, но архитектура должна позволять продавать любые категории товаров:

* мебель;
* бытовую технику;
* товары для дома;
* инструменты;
* освещение;
* текстиль;
* декор;
* электронику;
* детские товары;
* другие категории, добавляемые администратором.

## 1.3. Основная идея

Пользователь должен иметь возможность:

1. Открыть сайт с телефона или компьютера.
2. Просматривать категории и товары.
3. Искать и фильтровать товары.
4. Смотреть фотографии и характеристики товара.
5. Добавлять товары в корзину и избранное.
6. Зарегистрироваться с настоящим подтверждением email.
7. Указать адрес и оформить заказ.
8. Смотреть статус своих заказов.
9. Оставлять отзывы после покупки.
10. Получать email-уведомления.

Администратор должен управлять магазином через отдельную панель:

* категориями;
* товарами;
* фотографиями;
* характеристиками;
* остатками;
* заказами;
* пользователями;
* отзывами;
* скидками;
* баннерами;
* промокодами.

---

# 2. Цель проекта

Создать быстрый, безопасный и расширяемый интернет-магазин, который:

* работает как настоящее коммерческое приложение;
* имеет современный frontend на Next.js;
* имеет отдельный REST API на Django REST Framework;
* поддерживает подтверждение email;
* использует PostgreSQL;
* готов к дальнейшему масштабированию;
* может быть развёрнут на настоящем сервере;
* позволяет добавлять новые категории без изменения программного кода.

---

# 3. Формат разработки и обучения

Проект создаётся не путём слепого копирования готового кода.

Каждый модуль разрабатывается в учебно-практическом формате.

Для каждого этапа необходимо:

1. Объяснить, какую проблему решает модуль.
2. Объяснить архитектуру до написания кода.
3. Показать связь между моделями, API и frontend.
4. Писать код небольшими логическими частями.
5. Объяснять каждое непонятное поле, класс, метод и импорт.
6. После каждого блока проверять работу через Swagger, Postman или frontend.
7. Разбирать найденные ошибки, а не просто заменять код.
8. Объяснять, почему выбран конкретный способ реализации.
9. Рассматривать важные альтернативы и их недостатки.
10. После завершения модуля давать практическое задание для самостоятельной проверки.

Готовый код должен соответствовать реальной архитектуре проекта и не создаваться в отрыве от уже существующих моделей, serializers, views, services и frontend-компонентов.

# 4. Архитектура проекта

Проект состоит из двух независимых частей.

```text
Sifat-Mebel
│
├── backend/      Django REST Framework API
│
└── frontend/     Next.js web application
```

Связь между ними происходит через HTTP API.

```text
Пользователь
     ↓
Next.js Frontend
     ↓ HTTP/HTTPS
Django REST API
     ↓
PostgreSQL / Redis / Email / Storage
```

Необходимо создать собственную модель пользователя на основе `AbstractUser` или `AbstractBaseUser`.

Основным идентификатором для входа должен быть email.

Поля:

```text

email
phone_number
first_name
last_name
role
is_active
is_staff
is_email_verified
date_joined
last_login
created_at
updated_at
```

Требования:

* email уникальный;
* email хранится в нормализованном виде;
* пароль хранится только в хешированном виде;
* удалённый пользователь не должен ломать историю заказов;
* роли реализуются через отдельное поле и permissions;
* при регистрации email считается неподтверждённым.

# 9. Регистрация и подтверждение email

## 9.1. Регистрация

Пользователь отправляет:

```json
{
  "email": "user@example.com",
  "password": "strong-password",
  "password_confirm": "strong-password",
  "first_name": "Ali",
  "phone_number": "+992..."
}
```

Backend должен:

1. Проверить формат email.
2. Проверить уникальность email.
3. Проверить совпадение паролей.
4. Проверить надёжность пароля.
5. Создать пользователя.
6. Установить `is_email_verified = false`.
7. Создать код подтверждения.
8. Отправить настоящий email.
9. Не возвращать пароль в ответе.

## 9.2. Код подтверждения

Используется 6-значный цифровой код.

Модель `EmailVerificationCode`:

```text
id
user
code_hash
purpose
expires_at
attempts
is_used
created_at
```

Требования:

* код действует ограниченное время, например 10 минут;
* код нельзя использовать дважды;
* новый код делает старый недействительным;
* код не желательно хранить в базе в открытом виде;
* количество неправильных попыток ограничивается;
* повторная отправка имеет cooldown;
* endpoint защищается rate limiting;
* после подтверждения устанавливается `is_email_verified = true`.

## 9.3. Повторная отправка кода

Пользователь может запросить новый код.

Ограничения:

* нельзя отправлять код каждую секунду;
* необходимо показывать время до следующей отправки;
* слишком частые запросы временно блокируются;
* нельзя сообщать постороннему человеку, зарегистрирован email или нет, если это создаёт риск enumeration.

## 9.4. Вход

Вход выполняется по email и паролю.

После успешного входа backend возвращает:

* access token;
* refresh token;
* краткую информацию о пользователе.

Неподтверждённый пользователь не должен получать полный доступ к оформлению заказа и личным функциям.

## 9.5. JWT

Используются:

* короткоживущий access token;
* долгоживущий refresh token;
* обновление access token;
* blacklist refresh token при logout;
* ротация refresh token;
* возможность выйти со всех устройств.

Для production предпочтительно хранить refresh token в безопасной `HttpOnly Secure` cookie.

## 9.6. Восстановление пароля

Процесс:

1. Пользователь вводит email.
2. Система отправляет код или безопасную ссылку.
3. Пользователь подтверждает запрос.
4. Устанавливает новый пароль.
5. Старые refresh token становятся недействительными.

## 9.7. Смена email

Смена email требует:

* ввода пароля;
* подтверждения нового email;
* уведомления старого email;
* временного хранения нового адреса до подтверждения.

Необходимо контролировать наличие.

Поля:

```text

```

Доступное количество:

```text
available = stock_quantity - reserved_quantity
```

Требования:

* нельзя заказать больше доступного количества;
* при оформлении товар резервируется;
* после отмены заказа резерв возвращается;
* после подтверждённой продажи остаток уменьшается;
* администратор получает предупреждение о низком остатке;
* все изменения остатка желательно сохранять в журнале.

# 23. Оформление заказа

Процесс checkout:

1. Пользователь открывает корзину.
2. Backend проверяет наличие товаров.
3. Пользователь выбирает или вводит адрес.
4. Выбирает способ доставки.
5. Выбирает способ оплаты.
6. Вводит комментарий.
7. Применяет промокод.
8. Проверяет итоговую стоимость.
9. Подтверждает заказ.
10. Backend создаёт заказ атомарно.
11. Товары резервируются.
12. Пользователю отправляется письмо.
13. Администратор получает уведомление.

Операция должна выполняться внутри транзакции базы данных.

# 58. Правила качества кода

Backend:

* бизнес-логика не должна полностью находиться во views;
* сложная логика выносится в services;
* запросы выносятся в selectors при необходимости;
* serializers отвечают за представление и валидацию;
* модели защищают основные инварианты;
* операции заказа используют транзакции;
* исключается дублирование;
* используются понятные названия;
* добавляются type hints там, где они полезны;
* создаются индексы;
* контролируется количество SQL-запросов.

Frontend:

* компоненты должны быть небольшими;
* бизнес-логика не дублируется;
* API-вызовы не располагаются хаотично;
* все данные типизированы;
* формы используют общие схемы;
* общие UI-компоненты переиспользуются;
* Server Components используются по умолчанию;
* `"use client"` добавляется только при необходимости;
* ошибки показываются пользователю понятно;
* loading-состояния обязательны.

```text
3. Создать CustomUser.
4. Настроить вход по email.

8. Подключить SMTP.
9. Отправить настоящее письмо.
10. Создать endpoint подтверждения.
11. Добавить повторную отправку.
12. Добавить ограничения попыток.
13. Подключить JWT.
14. Создать страницы Next.js:
    - register;
    - verify-email;
    - login.
```

```text
Пользователь открывает Next.js-сайт
```
